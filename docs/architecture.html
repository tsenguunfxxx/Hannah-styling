01 — Тойм

Систем ерөнхийдөө хэрхэн ажиллах вэ

Энэ бол нэг Next.js төсөл. Frontend, backend хоёр тусдаа сервер биш — нэг код дотор хамт байна. Next.js-ийн App Router нь өгөгдлийг серверт татаж, бэлэн HTML-ийг хөтөч рүү илгээдэг тул хурдан бөгөөд SEO сайн байна.

Кодыг ойлгоход хамгийн чухал зүйл бол гурван давхарга. Энэ дүрмийг барьвал төсөл хэзээ ч замбараагүй болохгүй:

1 — UI давхарга

app/ ба components/. Зөвхөн харагдах байдал. Энд prisma шууд дуудахгүй, SQL бичихгүй.

2 — Логик давхарга

lib/queries/ — өгөгдөл унших. actions/ — өгөгдөл бичих (Server Actions). Эрх шалгах, Zod-оор шалгах бүх ажил энд.

3 — Өгөгдлийн давхарга

prisma/schema.prisma ба Neon Postgres. Зөвхөн 2-р давхаргаас хандана.

Яагаад ингэж хуваадаг вэХэрэв component дотроо шууд database дууддаг бол нэг өдөр "энэ үнэ хаанаас ирээд байна аа?" гэж 40 файл ухах болно. Гурван давхарга нь: харагдах юм components/-д, бодох юм actions/-д, хадгалах юм prisma/-д гэсэн энгийн дүрэм.

Server Component vs Client Component

Next.js-д component бүр анхнаасаа Server Component. Энэ нь серверт ажиллаад database руу шууд хандаж чадна, гэхдээ onClick, useState ашиглаж чадахгүй. Дээр нь "use client" бичвэл Client Component болж, интерактив болдог ч database руу хандаж чадахгүй.

Хамгаалалт хаана хийгдэх вэ

Хоёр давхар хамгаалалт тавина. middleware.ts нь хурдан шүүлт хийж /admin руу орох гэсэн зочныг /login руу шидэнэ. Гэхдээ жинхэнэ хамгаалалт нь Server Action бүрийн эхний мөрөнд байна:

// actions/admin/product.action.ts
async function requireAdmin() {
  const session = await auth();
  if (session?.user.role !== "ADMIN") {
    throw new Error("Танд энэ үйлдлийг хийх эрх байхгүй.");
  }
  return session;
}

Учир нь middleware-ийг тойрч шууд action дуудах боломжтой. Сервер талын шалгалтгүй бол хамгаалалт байхгүй гэсэн үг.

Диаграм 01 — Model-уудын холбоос

Хамгийн чухал 4 model

ModelГол талбаруудЮуны төлөө
Product id, name, slug, description, basePrice, discountPrice, categoryId, isFeatured, isActive, soldCount, createdAt Барааны ерөнхий мэдээлэл. Үлдэгдэл ЭНД байхгүй.
ProductVariant id, productId, size, color, colorHex, sku, stock, price? Өнгө + размер бүрийн тусдаа үлдэгдэл. Жинхэнэ зарагдах нэгж.
OrderItem id, orderId, variantId, productName, size, color, image, unitPrice, quantity Захиалсан үеийн үнэ ба нэрийг хуулж хадгална (snapshot).
Order id, orderNumber, userId, status, subtotal, shippingFee, discount, total, address, phone, note Захиалгын толгой. Төлөв энд өөрчлөгдөнө.

Prisma-гаар бичсэн жишээ

model ProductVariant {
  id        String  @id @default(cuid())
  productId String
  product   Product @relation(fields: [productId], references: [id], onDelete: Cascade)

  size      String   // "S" | "M" | "L" | "XL"
  color     String   // "Black"
  colorHex  String   // "#111111" — дугуй өнгө харуулахад
  stock     Int      @default(0)
  price     Int?     // хоосон бол product.basePrice-ийг ашиглана

  cartItems  CartItem[]
  orderItems OrderItem[]

  @@unique([productId, size, color])   // давхардахгүй
  @@index([productId])
}

@@unique([productId, size, color]) нь "Black / M"-ийг хоёр удаа үүсгэхээс сэргийлнэ. Үнийг Int-ээр (төгрөгөөр бүхэл тоо) хадгалж байгаа нь санамсаргүй биш — Float ашиглавал 0.1 + 0.2 = 0.30000000000000004 маягийн алдаа мөнгөн дүнд гарна.

05 — Relationship

Model-ууд яагаад ингэж холбогдож байна вэ

Product ба ProductVariant — 1 : N

"Premium Oversized Hoodie" бол нэг Product. Гэтэл хэрэглэгч үнэндээ "Хар өнгийн, M размерын hoodie"-г худалдаж авдаг. Тийм учраас:

Product: Premium Oversized Hoodie   (199,000₮)
  └─ Variant: Black / S  → stock 10
  └─ Variant: Black / M  → stock 15
  └─ Variant: Black / L  → stock  8
  └─ Variant: White / S  → stock  5
  └─ Variant: White / M  → stock 12

Сагс, захиалга бүгд Product руу биш, Variant руу холбогдоно. Ингэснээр "Black / M дууссан, White / M байгаа" гэдгийг систем яг таг мэднэ.

Order ба OrderItem — үнэ хөлдөх ёстой

Хамгийн олон эхлэгч алддаг газар. Хэрэв OrderItem зөвхөн variantId-г хадгалаад үнийг Product-оос уншдаг бол: маргааш админ үнийг 199,000₮ → 249,000₮ болгоход өчигдрийн захиалгууд бүгд өөрчлөгдөнө. Нягтлан бодох бүртгэл сүйрнэ.

Тиймээс OrderItem нь захиалга үүсэх мөчид productName, size, color, image, unitPrice-г хуулж авна. Бараа устсан ч хуучин захиалга бүрэн хэвээрээ харагдана.

Cart — зочин ба нэвтэрсэн хэрэглэгч

Cart нь userId (нэвтэрсэн) эсвэл sessionId (cookie-д хадгалагдсан зочин) хоёрын аль нэгтэй холбогдоно. Хэрэглэгч нэвтрэх үед зочны сагсыг хэрэглэгчийн сагстай нэгтгэнэ — ингэснээр "сагсалсан юм минь алга болчихлоо" гэсэн гомдол гарахгүй.

Category — өөртөө холбогдсон

Category нь parentId талбартай тул "Эмэгтэй → Даашинз" гэсэн мод үүсгэж чадна. Эхэндээ зөвхөн үндсэн 8 ангилал ашиглаад, дараа нь дэд ангилал нэмэхэд schema өөрчлөх шаардлагагүй.

Устгах үеийн дүрэмБараа устгахад түүний зураг, variant хамт устана (onDelete: Cascade). Гэхдээ захиалга хэзээ ч устахгүй — OrderItem нь variant руу onDelete: SetNull-ээр холбогдоно. Практикт бараа устгахын оронд isActive = false болгох нь илүү аюулгүй.

Диаграм 02 — Хэрэглэгчийн үндсэн урсгал

Анхаарах гурван зүйл:

  • Сагсалахад нэвтрэх шаардлагагүй. Зочин чөлөөтэй сагсална, зөвхөн checkout дээр нэвтэрнэ. Ингэснээр борлуулалт унахгүй.
  • Размер сонгоогүй бол "Сагсанд хийх" товч идэвхгүй. Сонголт хийсний дараа тухайн variant-ын үлдэгдлийг харуулна: "Үлдэгдэл: 3".
  • Үлдэгдлийг хоёр удаа шалгана — сагсанд нэмэхэд нэг удаа, захиалга үүсгэхэд дахин нэг удаа. Хоёр хүн зэрэг сүүлийн барааг авах гэж болзошгүй.

07 — Stock

Үлдэгдлийн систем

Энэ бол e-commerce-ийн зүрх. Буруу хийвэл байхгүй бараа зарагдана. Бүх ажиллагаа нэг transaction дотор явагдана — эсвэл бүгд амжилттай, эсвэл юу ч болохгүй.

// actions/order.action.ts — гол хэсэг
await prisma.$transaction(async (tx) => {

  for (const item of cartItems) {
    // Нөхцөлтэй хасалт: stock хүрэлцэж байвал л хасна
    const result = await tx.productVariant.updateMany({
      where: { id: item.variantId, stock: { gte: item.quantity } },
      data:  { stock: { decrement: item.quantity } },
    });

    if (result.count === 0) {
      throw new Error(`${item.name} (${item.color}/${item.size}) үлдэгдэл хүрэлцэхгүй байна.`);
    }
  }

  const order = await tx.order.create({ data: { /* items snapshot-той */ } });
  await tx.cartItem.deleteMany({ where: { cartId } });
  return order;
});

updateMany-г where: { stock: { gte: quantity } }-тэй хослуулсан нь санамсаргүй биш. Энэ бол атомик үйлдэл: database өөрөө нэг алхамд шалгаж хасна. Хэрэв эхлээд findUnique-ээр уншаад дараа нь update хийвэл, тэр хоёрын хооронд өөр хэрэглэгч мөн адил барааг авч, үлдэгдэл сөрөг болно.

НөхцөлҮлдэгдэлд юу болохХэрэглэгч юу харах
Захиалга үүсэхstock -= quantityЗахиалга амжилттай
Захиалга цуцлагдахstock += quantity (буцаана)Цуцлагдсан
Үлдэгдэл 0Өөрчлөгдөхгүй"Дууссан" — товч идэвхгүй
Үлдэгдэл 1–5Өөрчлөгдөхгүй"Зөвхөн 3 ширхэг үлдсэн"
Бүх variant 0ӨөрчлөгдөхгүйКарт дээр "SOLD OUT" тэмдэг

Цуцлах үед давхар буцаахаас сэргийлж Order.stockRestored гэсэн Boolean талбар нэмнэ. Нэг захиалгын үлдэгдлийг зөвхөн нэг удаа буцаана.
